# PRD — Zalo Account Connector

**Status:** Draft
**Last updated:** 2026-07-01
**Owner:** (TBD)

> This document describes *what* the Zalo connector must let users accomplish and *why* — the
> problem, the user goals, the data involved, the required inputs, and the setup flow. It is
> intentionally **UI-neutral**: it specifies requirements and behavior, not layout, components,
> or visual styling. Any screen that satisfies these requirements is a valid implementation.

---

## 1. Summary

Customers who run marketing and customer-engagement programs on Appier need to link their **Zalo
Official Account (OA)** so the platform can send messages, receive events, and use Zalo as a
delivery/engagement channel. Today there is no self-serve way to do this; connecting requires
manual, back-and-forth configuration between the Zalo developer portal and Appier.

This feature lets a customer **connect, view, and manage one or more Zalo Official Accounts**
themselves, through a guided setup that exchanges the required credentials and configuration
between Zalo and Appier.

---

## 2. Background & problem

Zalo is a dominant messaging platform in several of our markets. To use it as a channel, Appier
must be authorized against the customer's Zalo Official Account and app, and both sides must be
configured to trust each other (domain verification, callback and webhook endpoints, secret
exchange).

**Problems today**
- No self-service path — connecting an account is a manual, support-assisted task.
- The Zalo setup requires values that are *generated by Appier* (callback/webhook/domain URLs) and
  values that are *held by the customer* (app ID, secrets). Users don't have a single place that
  tells them which value goes where.
- There is no visibility into whether a connected account is healthy, so failures are discovered
  late (e.g. campaigns silently fail to deliver).

**Why now** — Zalo channel demand is growing, and support-driven onboarding does not scale.

---

## 3. Goals & non-goals

### Goals
- Let a user connect a Zalo Official Account without engineering or support involvement.
- Support **multiple** connected accounts per project.
- Give users an at-a-glance **health status** for each connection.
- Make the exchange of Appier-generated values ↔ Zalo-portal configuration explicit and guided.
- Let users **reconnect / repair** a broken connection and **remove** a connection.

### Non-goals (this release)
- Composing or sending Zalo messages/campaigns (handled by downstream messaging features).
- Managing Zalo *content* templates or message approval.
- Connecting other channels (LINE, WhatsApp, etc.) — though the model should not preclude them.
- Team-level permission/role design beyond existing project access controls.

---

## 4. Users & personas

| Persona | Description | Relationship to this feature |
|---|---|---|
| **Marketing operator** | Sets up and runs engagement programs. Not necessarily technical. | Primary user; initiates and monitors connections. |
| **Technical admin / developer** | Has access to the customer's Zalo developer portal and secrets. | Provides credentials; performs the Zalo-side configuration. |
| **Appier support / CSM** | Assists onboarding today. | Should be *removed from the loop* for the common case. |

The two customer personas are often **different people**, so the flow must tolerate being paused
and resumed (one person starts it, another completes the Zalo-portal steps).

---

## 5. User goals & needs (jobs to be done)

- *"I want to connect my company's Zalo Official Account to Appier so I can use it as a channel."*
- *"I need to know exactly which values to copy where — without reading external docs end-to-end."*
- *"I want to manage several Official Accounts from one place."*
- *"I want to see at a glance whether each connection is working, and fix it when it isn't."*
- *"I want to hand the technical part to a colleague and pick it back up when they're done."*
- *"I want to disconnect an account when we stop using it."*

**Needs that follow from these**
1. A list of existing connections with clear, trustworthy status.
2. A single, guided setup that surfaces both the values the user must supply and the values Appier
   generates for them to paste into Zalo.
3. Validation and clear error messaging at each step.
4. Ability to resume an incomplete setup.
5. Ability to edit/reconnect and to remove a connection.

---

## 6. Scope of capabilities

### 6.1 Connection list / management
- View all Zalo connections in the current project, each showing at minimum: **account identity**,
  **status**, and a **reference URL/identifier** for the Official Account.
- Start a **new connection**.
- Per-connection actions: **open/view details**, **reconnect/repair**, **remove**.
- Handle the **empty state** (no connections yet) with a clear call to action.

### 6.2 Connection setup (guided)
A multi-step flow that collects customer credentials, exchanges generated configuration, and
completes authorization. See [§8 Setup flow](#8-setup-flow--steps).

### 6.3 Status & health
Each connection has a status the user can trust (see [§9 Statuses](#9-connection-statuses)).

---

## 7. Required fields

Fields fall into two categories: **user-supplied inputs** (the user enters them) and
**system-generated values** (Appier produces them; the user copies them into the Zalo portal).

### 7.1 User-supplied inputs

| Field | Required | Description | Validation / notes |
|---|---|---|---|
| **Zalo Application ID** | Yes | Identifier of the customer's Zalo app, from the Zalo for Developers portal. | Non-empty; format-checked against Zalo's ID pattern; must resolve to a real app at verification time. |
| **Application secret key** | Yes | The app's secret, paired with the Application ID. | Non-empty; treated as a **secret** (masked input, never displayed after save, stored encrypted). |
| **OA Secret Key** | Yes | Secret of the specific Official Account being linked. | Non-empty; **secret** handling as above. |

> Additional identity fields (Official Account name, avatar, OA ID) are expected to be **retrieved
> from Zalo** after authorization rather than typed by the user.

### 7.2 System-generated values (provided *to* the user)

These are produced by Appier once the app credentials are accepted, and must be copied by the user
into the corresponding places in the Zalo developer portal.

| Value | Purpose | Where the user pastes it (Zalo side) |
|---|---|---|
| **Domain URL** | Proves Appier controls the domain Zalo will call. | Zalo → Domain authentication. |
| **Official Account Callback URL** | Endpoint Zalo redirects to during OA authorization. | Zalo → General Settings. |
| **Webhook URL** | Endpoint Zalo posts events/messages to. | Zalo → Webhook. |

**Rules**
- These values must be **read-only** and easy to copy.
- They should exist only after the prerequisite step completes; before that, communicate that they
  are pending (do not show stale or blank values with no explanation).
- Values must be **stable** for a given connection so the user can re-copy them later without them
  changing underneath an already-configured Zalo portal.

## 8. Setup flow / steps

The flow is inherently **sequential with an external hop**: the user does something in Appier, then
something in the Zalo portal, then returns to Appier. It must be resumable.

### Step 1 — Provide app credentials
- **Input:** Zalo Application ID, Application secret key.
- **Action:** User submits (e.g. "Continue").
- **System:** Validates the credentials with Zalo. On success, **generates** the Domain URL,
  Callback URL, and Webhook URL for this connection.
- **Exit criteria:** Both fields valid and accepted; generated URLs now available for Step 2.

### Step 2 — Configure the Zalo portal & supply OA secret
- **What the user does (external):** In the Zalo for Developers portal, paste the generated
  **Domain URL** (Domain authentication), **Callback URL** (General Settings), and **Webhook URL**
  (Webhook).
- **Input (in Appier):** OA Secret Key.
- **Guidance:** The step must clearly state which generated value goes to which Zalo location, and
  link to the relevant Zalo portal pages and a setup guide.
- **Exit criteria:** OA Secret Key provided; Zalo-side configuration completed by the user.

### Step 3 — Authorize
- **Action:** User initiates authorization (e.g. "Authorize").
- **System:** Runs the OA authorization/OAuth handshake with Zalo using the configured callback,
  retrieves the Official Account identity, and finalizes the connection.
- **Exit criteria:** Zalo confirms authorization → connection is created/updated with status
  **Connected** and appears in the list.

### Flow rules
- **Resumable:** A partially completed setup can be saved and continued later (possibly by a
  different user). Re-entering shows the correct step with previously entered non-secret values
  preserved.
- **Cancelable:** The user can abandon setup without creating a connection.
- **Ordering enforced:** Step 3 cannot succeed before Step 1 (no generated URLs) and the Zalo-side
  configuration exist; the flow should prevent or clearly block out-of-order completion.
- **Idempotent verification:** Re-running authorization for the same OA should update, not
  duplicate, the connection.

## 9. Connection statuses

At minimum the following states, each with a clear label and description:

| Status | Meaning | User action implied |
|---|---|---|
| **Connected** | Authorized and healthy; usable as a channel. | None. |
| **Error** | Authorization or connectivity failed (e.g. revoked secret, misconfigured webhook, expired authorization). | Reconnect / repair; view the reason. |
| **Pending / Incomplete** *(recommended)* | Setup started but not finished. | Resume setup. |
| **Disconnected** *(recommended)* | Previously connected, now inactive (removed on Zalo side or by user). | Reconnect or remove. |

- Status must reflect **real health**, not just "setup finished" — surface failures detected after
  connection (e.g. webhook rejections, auth expiry).
- An **Error** status should expose a human-readable reason and a path to fix it.

---

## 10. States & edge cases

- **Empty list:** No connections → explain the feature and offer to start one.
- **Invalid credentials (Step 1):** Reject with a specific, actionable message; do not generate URLs.
- **Incomplete Zalo-side config (Step 3):** Authorization fails → explain likely cause (which URL
  is missing/misconfigured) and let the user retry.
- **Duplicate account:** Attempting to connect an OA that is already connected in the project →
  detect and either block or route to the existing connection.
- **Secret rotation:** User rotates a secret on Zalo → connection moves to Error; user updates the
  secret via reconnect/repair.
- **Revoked authorization:** Zalo authorization revoked externally → status reflects it.
- **Removal:** Removing a connection stops its use as a channel and requires confirmation
  (destructive action). Define whether in-flight/scheduled sends are affected.

---

## 11. Data model (conceptual)

**Connection** (per Official Account, per project)
- `id`, `project_id`
- `application_id` (Zalo app ID)
- `application_secret` *(secret, encrypted)*
- `oa_secret` *(secret, encrypted)*
- `oa_identity` — retrieved from Zalo: OA name, OA ID, avatar, reference URL
- `generated.domain_url`, `generated.callback_url`, `generated.webhook_url`
- `status`, `status_reason`
- `created_at`, `updated_at`, `authorized_at`

Secrets are never returned to the client after save and are stored encrypted at rest.

---

## 12. Non-functional requirements

- **Security:** All secrets encrypted at rest and in transit; masked in the UI; excluded from logs.
- **Auditability:** Record who connected/removed/reconnected an account and when.
- **Reliability:** Webhook endpoint must handle Zalo's delivery/retry semantics; verify signatures.
- **Observability:** Detect and surface post-connection failures to drive the Error status.
- **Localization:** Copy and guidance must be translatable (Zalo's core markets are non-English).
- **Access control:** Respect existing project-level permissions for who may manage connections.

---

## 13. Success metrics

- **Self-serve completion rate:** % of started setups that reach **Connected** without support.
- **Time to connect:** median time from Step 1 to Connected.
- **Support deflection:** reduction in connector-related support tickets.
- **Connection health:** % of connections in **Connected** vs **Error** over time.
- **Repair success:** % of Error connections successfully reconnected by the user.

---

## 14. Open questions

1. Do we need **verification checks** for each generated URL (confirming the user pasted it into
   Zalo correctly) before allowing Step 3, or is authorization the only gate?
2. What is the exact **duplicate policy** (block vs. adopt existing) when an OA is already connected?
3. How are **in-flight/scheduled sends** handled when a connection is removed or errors out?
4. Is there a **"Step 3"** confirmation the user must return to (as the copy implies), or does
   authorization complete the flow directly?
5. What identity fields can we reliably **retrieve from Zalo** vs. must be entered manually?
